## 一、确认的缺陷（按严重度排序）

### 🔴 高：WebDAV 协议基本不可用（三处路径全部有问题）

WebDAV 是项目声明支持的三大协议之一，但实际三条挂载路径都有问题，导致 WebDAV 磁盘几乎挂不上或挂到错误位置。

**1. 系统挂载器拼错了 URL scheme**
- 位置：`MountService.swift:406`（`connectionURL`）
  ```swift
  var s = "\(drive.proto == .smb ? "smb" : (drive.proto == .nfs ? "nfs" : "https"))://"
  ```
- 问题：`mount volume "https://…"` 不被 AppleScript / NetFS 识别为 WebDAV 挂载。正确的 scheme 是 `webdav://` 或 `webdavs://`。结果：`viaSystemMount` 对 WebDAV 必然失败。
- 连带影响：默认（无自定义挂载点）的 WebDAV 走「系统挂载器优先」策略，失败后只能退回「直连」——而直连进不了 `/Volumes`，又落到 `~/Volumes`，把项目专门修复过的「路径统一」问题又带回来了。

**2. 兜底 `open` 也用了 `https`**
- 位置：`MountService.swift:261`（`viaOpenURL`）
  ```swift
  comps.scheme = drive.proto == .smb ? "smb" : (drive.proto == .nfs ? "nfs" : "https")
  ```
- 问题：`open "https://…"` 在 macOS 上是用浏览器打开网页，不是挂载磁盘。应改用 `webdav` / `webdavs`。

**3. 直连挂载（mount_webdav）漏了账号密码和端口**
- 位置：`MountService.swift:241-245`
  ```swift
  let url = "https://\(drive.host)\(enc(path))"          // 没有 user:pass，没有 :port
  result = Shell.run("/sbin/mount_webdav", ["-o", options.joined(...), url, mountPoint], ...)
  ```
- 问题：SMB 直连分支（`230-237` 行）正确地把 `user:pass@host:port` 拼进了 URL，但 WebDAV 分支完全没拼。后果：
  - 带密码的 WebDAV：直连因缺少凭据认证失败（而这条路径恰好只在「有密码」时才被启用，见 `120-122` 行）。
  - 自定义端口的 WebDAV（如 5006）：端口被忽略，永远连错端口。
- 修复建议：WebDAV 分支参照 SMB 分支，拼成 `webdav(s)://user:pass@host:port/path`，并统一 scheme 常量。

> 结论：WebDAV 是目前最脆弱的协议，建议优先修。SMB / NFS 不受影响。

### 🟠 中：挂载匹配可能认错「不同服务器的同名共享」

- 位置：`MountScanner.swift:116-119`（`match` 第 3 步）
  ```swift
  if !share.isEmpty {
      let byShare = volumes.filter { $0.shareName.lowercased() == share }
      if let best = preferred(byShare) { return best }   // 只看共享名，不看服务器
  }
  ```
- 问题：当磁盘配置指向服务器 A 的某个共享（如 `Data`），但 A 当前没挂、而服务器 B 恰好也暴露了同名共享 `Data` 且已挂载时，会错误返回 B 的卷，界面显示 A「已挂载」。更糟的是：用户点这块盘的「卸载」，会**误卸载掉 B 服务器上的共享**。
- 影响：数据/连接被错误操作。注释里以「双挂代价 > 认错代价」为由放行，但这只在「同一台 NAS」场景成立；跨两台不同 NAS 同名共享时就是 BUG。
- 修复建议：第 3 步应至少排除「服务器键明显不同（如一边 IP、一边主机名且无法解析为同一台）」的卷；或改为只在 `aliases` 为空（用户没填任何可识别主机）时才按共享名兜底。

### 🟠 中：重启后「挂载来源」标签永远显示「系统/访达挂载」

- 位置：`DriveStore.swift:24`（`appMounted` 仅内存）+ `DriveStore.swift:770-776`（`snapshot` 据此出标签）
- 问题：`appMounted` 集合不持久化，每次启动清空。于是本次运行由网盘管家自己挂上的盘，下次启动后都显示成「系统/访达挂载」。虽然不影响功能，但会误导用户判断「这块是谁挂的」。
- 修复建议：用 `UserDefaults` 持久化 `appMounted`（或反过来：持久化「用户手动卸载」的集合，启动时据此反向判断）。

### 🟠 中：界面无法清除已保存的密码

- 位置：`AppController.swift:560-573`（save 取 password）+ `DriveStore.swift:296`（`upsert` 只在不空时保存）
  ```swift
  if let password, !password.isEmpty {              // 空密码被直接忽略
      Keychain.save(password: password, for: drive)
  }
  ```
- 问题：用户若想把某块盘的密码「清空」，在编辑框留空保存时会被 `!password.isEmpty` 跳过，旧密码永远留在钥匙串。要改只能删掉整块盘再重建。属于安全/隐私 + 体验缺陷。
- 修复建议：`upsert` 区分「未提供」（保持原值）和「明确清空」（删除钥匙串项）。前端可传一个标记（如 `password === ""` 且带 `clearPassword` 标志）。

### 🟡 低–中：直连 SMB 的 `soft` 挂载选项可能不被 `mount_smbfs` 支持

- 位置：`MountService.swift:226`
  ```swift
  var options = ["soft", "nosuid", "nodev"]
  ```
- 问题：`soft` 是 NFS 选项；`mount_smbfs` 的可用选项有限，项目自己在 `Models.swift` 注释里也写过 `mount_smbfs -o vers=2.1` 实测报 `option not supported`。若 `soft` 不被接受，系统挂载器失败后的「直连兜底」会连带失败，SMB 磁盘彻底挂不上。
- 建议：实测 `mount_smbfs -o soft,nosuid,nodev`；若报错则去掉 `soft`（或仅在 NFS 分支使用）。

### 🟡 低：主线程扫挂载表（与项目自身约定冲突）

- 位置：`DriveStore.swift:311`（`upsert` 内 `volumes = MountScanner.scan()`）
- 问题：`refresh()` 的注释明确说「扫描要 fork `/sbin/mount`，绝不能占主线程」，但 `upsert` 直接在主线程扫。保存磁盘时会轻微卡顿一下（fork 子进程）。建议和 `refresh` 一样放到后台。

## 二、低优先 / 边界问题

1. **NetBIOS 主机名不缓存 IP**（`DriveStore.swift:409`）：`rememberIP` 的守卫是 `drive.host.contains(".")`，纯 NetBIOS 名（不含点）被跳过，导致每次挂载都重新解析（`.local` 首次解析可达 5–10 秒），无功能错误但慢。
2. **健康检查僵尸读取**（`MountWatchdog.swift:14-25`）：超时返回 `false` 后，后台那个 `contentsOfDirectory` 读仍在跑（kernel 级 soft 挂死可能远超 5 秒），会悄悄堆积阻塞线程。建议对超时的盘改用更强的探测或显式超时。
3. **发现结果数组的下标竞态**（`AppController.swift:325-356`）：`enrichDiscovered` 的多个异步块在 `main.async` 里按下标写 `self.discovered[i]`，若用户中途再次点「发现」重建了数组，可能出现下标越界或写错位置。
4. **导入即自动挂载**（`MountScanner.swift:198`）：`adoptableVolumes` 把「系统里已挂载」的盘一律设 `autoMount = true`。用户用访达挂过一次别人的共享，之后每次启动都自动挂，可能出乎意料。
5. **NFS 只能给提示**（`MountService.swift:142-146`）：NFS 真正挂载需要 `sudo`，代码只生成一条终端命令提示用户手动执行，无实际挂载路径（属于已知限制，但体验上应更明确）。
6. **诊断可能留下未挂载状态**（`MountService.swift:321-340`）：`diagnoseSMB` 每轮先强制卸载再试，若四个版本全失败，原本健康的盘会停在「未挂载」。

## 五、补充审查（2026-10-28）— 续查新增发现

> 本轮在既有报告基础上，重读了 `MountService.swift` / `Shell.swift` / `Keychain.swift` / `Models.swift` / `AppController.swift` / `StatusPopover.swift` / `StatusBarController.swift`，新增如下发现（与前面不重复）。

### 🔴 高（安全）：凭据经进程参数泄露，可被本机 `ps` 读取

- 位置：`MountService.swift:221`（`viaSystemMount` 把含密码的 URL 拼进 AppleScript，再以 `-e` 参数传给 `/usr/bin/osascript`）；`MountService.swift:260`（`viaDirectMount` 把 `//user:pass@host/share` 作为 argv 传给 `/sbin/mount_smbfs`）。
- 问题：两处都把**明文密码写进了子进程的命令行参数**。同一台 Mac 上的任何本地用户（或别的进程）执行 `ps -ax` / `ps aux` 都能在挂载瞬间看到完整密码。本项目的 `Keychain.swift` 注释里恰恰把"密码进命令行参数"列为要避免的安全风险（因为 `ps` 能看到），但 `MountService` 违反了这条原则。
- 影响：本地信息泄露。单用户 Mac 危害有限，但在多用户 / 共享 / 被投毒的机器上，凭据会被轻易拿走。
- 修复建议：
  - `osascript` 路径：脚本写临时文件再 `osascript <file>`，或 `printf '%s' "<script>" | osascript -` 走 stdin，避免密码出现在 argv。
  - `mount_smbfs` 路径：`mount_smbfs` 支持从 stdin 读取密码（运行时不把密码写进 URL 的 argv），或引用临时文件；彻底不把密码放进命令行。
  - 说明：`Shell.run` 用 `Process` + 参数数组、**不走 shell**，所以不存在 shell 注入；问题纯粹是"参数可见性"。

### 🟠 中：`isReachableHost` 在 DNS 超时时误判"可达"，放行错误主机

- 位置：`MountService.swift:412`
  ```swift
  if sem.wait(timeout: .now() + 2.5) == .timedOut { return true }
  ```
- 问题：解析超时（2.5s）时返回 `true`（放行），本意是别让 `.local` 慢解析卡住预检。副作用：主机名写错、或一台确实不可达且解析挂起的设备，会被当"可达"继续走真正的挂载（再等 14–20s 才失败）。不算功能错误，但让"连不上"的反馈变慢、并掩盖真正错因。
- 建议：区分"慢"与"不可达"——对纯 NetBIOS / `.local` 名超时放行，对明确 IP / 域名超时视为不可达；或在失败时给出更准的提示。

### 🟡 低（已修复）：面板"上半部分被裁切"

- 位置：`StatusPopover.swift`（`loadView` + `applySizeIfNeeded`）。
- 问题：面板区块按"建面板那一刻的高度"用绝对 frame 从上往下排；当磁盘数量变化使 `NSPopover.contentSize` 变小（如少了一块盘）时，窗口被压矮、子视图却停在旧 y 坐标，顶部区块被裁掉，表现为"上半部分没显示"。代码只更新了列表滚动区高度，未重排其余区块。
- 修复：新增 `layoutContent(height:)`，高度一变就把所有区块按新高度重排，并让容器贴合新高度，再通知外层改 `contentSize`。已重新构建安装验证。

### 🟡 低（健壮性/运维）：配置无锁，运行时改 `drives.json` 会被静默覆盖

- 现象：App 内存持有磁盘列表，任何 `persist()`（启动挂载、记住 IP、增删改等都会触发）都用内存状态整体覆盖 `drives.json`。若在 App 运行时手改该文件，下次 `persist()` 会把它冲掉。本次排障中，手动加的第 3 块"整台NAS"盘就是因此被覆盖丢失的（非代码 bug，属运维陷阱）。
- 建议：除非通过 App 自身增删改，否则不要在 App 运行时直接编辑 `drives.json`；若要支持热更新，可加"配置变更后 reload"或文件锁。

### 复核：此前 P0 / P1 仍处未修复状态

- **P0 WebDAV**：`connectionURL`（L430）与 `viaOpenURL`（L283）对 WebDAV 仍用 `https://` 而非 `webdav(s)://`，`mount volume "https://..."` 不会被识别为 WebDAV 挂载；`viaDirectMount` 的 WebDAV 分支（L265）仍漏 `user:pass` 与端口。建议优先修复。
- **P1 清除密码**：`upsert`（DriveStore L305）仅在密码非空时保存，编辑时留空无法清除已存密码；需前端传"明确清空"信号（如 `clearPassword:true`）后调用 `Keychain.delete`。

### 6.3 P2 — 工程化（长期最值钱，也是目前最大的空白）

1. **没有版本控制**〔确证〕：项目目录不是 git 仓库，源码放在 SMB 卷上，靠 `dist/` 里 1.4.3/1.4.4/1.4.5 的 dmg/pkg（含 `_旧构建残留`）当「版本」。这意味着**改坏了无法回滚、无法 diff、无法知道某行是哪个版本改的**。建议本地 `git init`（不必推远端）+ 每次发布打 tag；这是投入 10 分钟、收益最大的一项。
2. **零自动化测试、零 CI**〔确证〕：没有 Tests/、Package.swift、Makefile。而 `serverKey` 归一化、`MountScanner` 解析、`sourceShare`、`redact`、URL 编码、退避算法全是纯函数，非常适合一组不依赖 GUI 的单测；现在每次改动只能靠 `./build.sh` + 手工点。建议先给这 6 个纯函数补断言脚本/CI。
3. **无可观测性**〔确证〕：源码里没有 `os_log` / `Logger`，也没有崩溃捕获与「一键导出诊断」。用户报障只能 `NETMOUNT_LOG=1` 重启复现。建议加环形内存日志 + 「导出诊断包」（脱敏后含最近 N 轮看门狗决策、挂载返回码、配置摘要）。
4. **轮询偏重，可统一状态源**〔确证〕：主界面 4s ticker（每次 fork `/sbin/mount`）、面板 2s、watchdog 30s + 1s 倒计时、`NetworkContext` 每 10s fork 两次 `networksetup`（且 `wifiInterface()` 每次都重查硬件端口）。`StatusPopover.refresh()` 只读缓存，这点做得对。建议：网络接口名缓存、SSID 改按网络变化通知/更长节流、卷状态改事件驱动（`NSWorkspace` 卷挂载通知）+ 低频兜底，降低笔记本上的持续唤醒。
5. **单文件过大**〔确证〕：`DriveStore.swift` 985 行混合了持久化、状态、挂载编排、导入导出、诊断；`ui.html` 1583 行含全部界面与逻辑。改动时的回归面太大，建议按职责拆（不急着做，但配合 6.3-2 的单测一起最划算）。
6. **签名与分发**〔确证〕：`build.sh:56` / `package.sh:55` 用固定 DR `designated => identifier "com.keson.netmount"` 来锁住钥匙串授权，注释里已承认代价：**任何声明同一 bundle id 的程序都满足该 DR**，理论上可读统一密码库。这是 ad-hoc 签名的自觉取舍，不要简单拆成「一盘一条」（会退回每盘弹授权的老问题）。若要对外分发，应换正式 Developer ID 签名 + 公证，并在 DR 里加 `anchor apple generic`；同时考虑自动更新和 PKG 升级时的配置迁移/卸载残留。
7. **dist/ 与文档产物累积**〔确证〕：`dist/` 已 47MB + `_旧构建残留`，说明书 PDF 两份各约 4.8MB 且按 mtime 挑最新。建议保留最近 2 个版本，其余归档；生成脚本显式指定版本而不是挑 mtime。

### 6.4 复核确认无误（不要重复修）

- `ui.html` 所有 `innerHTML` 插值都过 `esc()`（`& < > " '`），`AppController.swift:226-233` 用 `JSONSerialization` 生成 JS 并转义 U+2028/2029 —— **未发现 XSS**。
- `appleScriptQuote()`（`MountService.swift:463-468`）按 `\\`→`"`→换行的顺序转义，用户名/密码/URL 三处都调用，脚本走 stdin 而非 `-e` —— **含引号、反斜杠、换行的密码不会破坏或注入 AppleScript**。
- `connectionURL` 不含任何凭据（改走 `as user name … with password …`），`Shell.run` 用参数数组不走 shell —— 密码不进 argv、无 shell 注入。
- `persist()` / `exportConfig()` 均为 `.atomic` 写入且调用点都在主线程；`load()` 解码失败先备份现场 —— 多来源不会写坏。
- 看门狗退避有 300s 上限、`notifiedDown` 去重、唤醒只排一个任务、`running` 串行；`timer` / `tickTimer` 创建与 `stop()` 配对正确；`StatusPopover.startRefresh` 先 invalidate 再建、用 `.common`。
- `Keychain` 用 `NSRecursiveLock` + update-first 写回；`MountHealth.isHealthy` 有 inFlight 去重；`isSafeMountPoint` 白名单算法本身正确（问题只在 `load()` 没调用）。
- `ui.html` 有 `prefers-color-scheme: dark` 适配；`Info.plist` 已配本地网络/AppleEvents 用途说明与 Bonjour 服务。
- 面板 `refresh()` 只读缓存，不 fork 子进程；`appMounted` 不持久化、访达手动推出后被挂回 —— 均为已确认的设计取舍。
